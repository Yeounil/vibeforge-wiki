# SA Ch2: 분산 시스템 핵심 속성

시스템 아키텍처 강의 2장. 분산 시스템 설계에서 다뤄야 할 7가지 핵심 속성을 비서 비유와 함께 설명한다.

## 요약

분산 시스템의 올바른 설계는 **일관성·가용성·파티션 허용성·지연 시간·내구성·신뢰성·확장성** 7개 속성의 트레이드오프를 이해하고 요구사항에 맞게 균형을 잡는 것이다. [[CAP 정리]]에 따라 파티션 허용성(P)은 현대 분산 시스템의 필수 전제이며, 파티션 발생 시 일관성(C)과 가용성(A) 중 하나를 선택해야 한다.

## 핵심 포인트

### 2.1 쓰기·읽기 옵션 비교 (3인 비서 비유)

**쓰기 방식**:
- **직렬 동기 쓰기**: 모든 노드 완료 확인 후 응답 → 정합성 최고, 지연 시간 최대
- **병렬 비동기 쓰기**: 지시 후 즉시 다음 업무 → 빠르지만 일시적 불일치 가능
- **메시징 서비스(Kafka/RabbitMQ)**: 게시판에 포스트잇 후 이탈 → 디커플링, 과부하 방지, 약간의 지연

**읽기 방식**:
- **단일 레플리카 읽기**: 빠르지만 stale 데이터 위험
- **전체 레플리카 읽기**: 최신·정확, 하지만 느리고 노드 장애 시 불가
- **쿼럼(Quorum) 읽기**: W+R>N 조건 → 속도·정확성 타협점 (과반수 응답으로 결정)

### 2.2 일관성 (Consistency)

[[일관성]] — 모든 노드가 동일한 데이터를 참조하도록 보장하는 특성.

- **강한 일관성**: 쓰기 후 모든 읽기가 항상 최신 값 반환. 엄격한 동기화, 선형 상태 보장.
- **최종 일관성**: 일시적 불일치 허용, 결국 수렴. 충돌 해결 기법:
  - **LWW (Last Write Wins)**: 타임스탬프 기준 덮어쓰기
  - **Vector Clocks**: 이력 추적 후 병합
  - **데이터 복제**: 비동기 전파 (SNS 프로필 변경 예시)
  - **가십 프로토콜**: 중앙 없이 무작위 이웃 노드 간 상태 교환 (Cassandra, DynamoDB)

### 2.3 가용성 (Availability)

[[가용성]] — 시스템이 장애 중에도 유효한 응답을 지속 제공하는 능력.

측정: **Nines** (예: 99.9% = 연간 8h45m 다운타임, 99.99% = 52분)

$$\text{Availability} = \frac{\text{Uptime}}{\text{Uptime} + \text{Downtime}}$$

핵심 방식:
- **다중화(Redundancy)**: SPOF 제거 — Active-Active / Active-Passive
- **로드 밸런싱**: 트래픽 분산 + 장애 노드 자동 차단
- **Heartbeat & Failover**: 주기적 신호 확인 후 자동 복구
- **무상태(Stateless) 아키텍처**: 세션을 외부 Redis 등에 저장 → 노드 교체 자유
- **블루-그린 배포**: 다운타임 없는 롤링 업데이트 가능

### 2.4 파티션 허용성 & CAP 정리

[[CAP 정리]] — 분산 시스템은 네트워크 파티션(P) 발생 시 일관성(C)과 가용성(A) 중 하나만 선택 가능.

- **네트워크 파티션**: 노드는 정상이지만 노드 간 네트워크 단절 (스플릿 브레인)
- **P는 필수**: 현대 분산 시스템에서 네트워크 장애는 상수(반드시 발생)
- **CP 시스템**: 파티션 발생 시 에러 응답, 데이터 정확성 우선 (예: 은행)
- **AP 시스템**: 구버전 데이터라도 응답, 가용성 우선 (예: SNS 피드)

### 2.5 지연 시간 (Latency)

$$\text{Total Latency} = \text{전파} + \text{전송} + \text{대기} + \text{처리}$$

5가지 단축 방식:
1. **네트워크 최적화**: 연결 풀링(Connection Pooling), HTTP/2·HTTP/3·gRPC
2. **캐싱**: Redis/Memcached(처리 지연↓), CDN(전파 지연↓)
3. **데이터 지역화**: 멀티 리전 배포, Read Replica 지리 분산
4. **비동기 통신**: 메시지 큐(Kafka)로 무거운 작업 분리 → HTTP 202 즉시 응답
5. **성능 튜닝**: DB 인덱싱·쿼리 최적화, GC 튜닝, OS 커널 파라미터

트레이드오프: 극단적 지연 감소 → 일관성 희생(Eventual Consistency), 처리량 저하(Spin-lock), 비용·복잡도 폭증

### 2.6 내구성 (Durability)

"'완료' 응답 후 서버 크래시가 나도 데이터는 반드시 보존" — ACID의 D.

핵심 방식:
- **WAL (Write-Ahead Logging)**: 변경 사항을 순차 로그로 디스크에 먼저 기록(`fsync()`)
- **동기식 복제**: 모든 백업 노드 ACK 후 응답 → 내구성 완벽, 지연 증가
- **비동기식 복제**: 주 서버만 쓰고 즉시 응답 → 빠르지만 주 서버 장애 시 유실 위험
- **쿼럼(W+R>N)**: Cassandra 등 — 지연·내구성 중간 타협

트레이드오프: 내구성↑ → 지연 시간↑, 동기 복제 + 파티션 발생 시 가용성↓

### 2.7 신뢰성 (Reliability)

**신뢰성 ≠ 가용성**: 가용성은 "지금 응답하는가"(상태 단면), 신뢰성은 "얼마나 오래 안 뻗는가"(시간 연속성).

예: 1시간마다 1초 크래시 → 가용성 99.97%, 신뢰성 낮음.

지표:
- **MTTF** (Mean Time To Failure): 다음 고장까지 평균 시간
- **MTTR** (Mean Time To Recovery): 복구까지 평균 시간
- **MTBF** = MTTF + MTTR

향상 방식:
- **N-Modular Redundancy**: 동일 연산 다중 실행 후 다수결 투표
- **우아한 성능 저하(Graceful Degradation)**: 핵심 기능만 유지, 부가 기능 일시 차단
- **체크포인팅 & 롤백**: 중간 상태 저장 → 크래시 후 재개
- **카오스 엔지니어링**: 넷플릭스 Chaos Monkey — 운영 중 의도적 장애 주입으로 취약점 사전 검증

### 2.8 장애 허용성 (Fault Tolerance)

"장애를 막는 것이 아닌, 장애가 전체로 번지지 않도록 국소화(Isolation)" — 신뢰성·가용성의 구체적 방어 메커니즘.

핵심 패턴:
- **다중화(Redundancy)**: N+1 또는 2N 컴포넌트 구성
- **서킷 브레이커(Circuit Breaker)**: B 서비스 반복 실패 시 연결 차단 → 연쇄 장애(Cascading Failure) 방지
- **벌크헤드(Bulkhead)**: 서비스별 스레드 풀 격리 → 이메일 서버 장애가 결제에 영향 X
- **지수적 백오프(Exponential Backoff)**: 재시도 간격 1s→2s→4s→8s 증가 → 재시도 폭풍 방지

트레이드오프: 비용 증가(30~50% 유휴 리소스), 아키텍처 복잡도 급증, 약간의 지연 추가

### 2.9 확장성 (Scalability)

[[확장성]] — 부하 증가 시 무리 없이 리소스를 늘릴 수 있는 능력.

**인스턴스**: 물리 서버를 가상화한 독립 가상 컴퓨터 (CPU·RAM·OS 할당)

| | 수직 확장 (Scale-up) | 수평 확장 (Scale-out) |
|--|---|---|
| 방법 | 단일 인스턴스 스펙 업그레이드 | 인스턴스 개수 증가 |
| 비유 | 슈퍼맨 1명 고용 | 평범한 직원 100명 고용 |
| 장점 | 단순성, 데이터 일관성 보장 | 무한 확장, 높은 가용성, 무중단, 비용 효율 |
| 단점 | 물리적 한계, 비용 비선형, SPOF | 복잡도↑, 상태 관리 어려움, 일관성 딜레마 |

실무 패턴: 앱 서버는 무상태(Stateless) + 수평 확장 / DB는 수직 확장 우선, 한계 도달 시 Replication·Sharding으로 수평 확장
