# SA Ch1: 시스템 설계 기초

시스템 아키텍처 강의 1장. [[시스템 설계]]의 정의·유형·중요성을 다룬다.

## 요약

[[시스템 설계]]는 기능적·비기능적 요구사항을 충족하기 위해 소프트웨어 시스템의 아키텍처·컴포넌트·인터페이스·상호작용을 정의하는 과정이다. 단일 프로그램부터 여러 노드로 구성된 분산 시스템까지 대상이 된다. 좋은 설계는 확장성·성능·유지 보수성·비용 효율성을 사전에 확보하게 해준다.

## 핵심 포인트

### 시스템 설계 6단계 (1.1)

1. **요구사항 분석** — 기능적·비기능적 요건 파악, 데이터 조회·저장 패턴 분석
2. **상위 수준 아키텍처 설계** — 컴포넌트·모듈·인터페이스의 전체 구조 정의
3. **하위 수준 상세 설계** — 핵심 비즈니스 로직 알고리즘·컴포넌트 간 상호작용 설계
4. **UI 설계** — 백엔드 서비스와 API로 통신할 사용자 인터페이스 정의
5. **API 설계** — 프론트엔드↔백엔드 통신 인터페이스 정의
6. **데이터베이스 설계** — 데이터 구조·저장 메커니즘 선택 (RDBMS / NoSQL 등)

### 상위 수준 설계 — 4가지 아키텍처 패턴 (1.2.1)

| 패턴 | 설명 |
|------|------|
| 모놀리식 | 모든 컴포넌트를 결합한 단일 애플리케이션 |
| 클라이언트-서버 | 클라이언트가 하나 이상의 서버에 서비스 요청 |
| 마이크로서비스 | 네트워크로 통신하는 작고 독립적인 다수의 서비스 |
| 이벤트 주도 | 비동기 이벤트·메시지로 컴포넌트 상호작용 |

설계 시 고려 축: 확장성·유지 보수성·신뢰성·지연 시간

### 데이터 흐름 설계 (1.2.1)

- **수집**: API 호출 / 실시간 스트리밍 / 배치 처리
- **저장**: 접근 빈도·검색 성능·일관성 요건에 따라 선택
- **처리**: 변환·분석·요약 — 컴퓨팅 자원·병목 사전 고려
- **검색**: 응답 시간·캐시·로드 분산 전략

### 하위 수준 설계 — API 하위 호환성 (1.2.2)

- **명시적 버전 관리(API Versioning)**: URI 경로 방식(`/v1/`, `/v2/`) 또는 헤더 방식
- **추가(Additive) 원칙**: 기존 필드 삭제·수정 대신 새 필드 추가만
- **어댑터 패턴**: v1 요청 → 어댑터가 v2 포맷으로 변환 → 핵심 로직 → v1 포맷 응답
- **DB 호환성**: 새 컬럼 추가, 과도기 스키마 유지 후 점진적 일몰(Deprecation)

### 하위 수준 설계 — 코드 최적화 기법 (1.2.2)

- **리팩터링**: 기능 유지하며 코드 구조 개선
- **루프 언롤링**: 반복문 제어 오버헤드 감소 (예: 100회 → 25회)
- **메모이제이션**: 동일 연산 결과 캐싱
- **병렬 처리**: 독립 하위 작업 동시 실행

### 시스템 설계의 이점 (1.3)

요구사항 명확화 / 협업 시너지 / 설계 검토 용이 / 높은 확장성 / 성능 병목 사전 방지 / 유지 보수성 향상 / 비용 효율성
